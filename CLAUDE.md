# MDPinn

## What this is

Research project investigating whether physics-informed loss terms (currently: momentum conservation) meaningfully improve neural-network molecular-dynamics surrogate models, built on TorchMD-Net's TensorNet architecture, versus plain supervised training on energies and forces.

**Environment split:** this checkout has no `torchmdnet`/CUDA installed (only `torch` in `.venv`, used for local `py_compile`/synthetic-test verification of code changes, and for running pure-Python analysis scripts against already-downloaded result CSVs). All actual training happens on a remote Linux box (checkpoint paths reference `/home/lachmadh/projects/MDPinn`). Code changes get committed here, synced over, and run there - nothing that imports `torchmdnet`/`lightning` can be executed end-to-end from this machine.

**Detailed research log:** `paper/main.tex` is a working paper/lab notebook tracking motivation, methods, math, results, and open questions in far more depth than this file - read it for the full water-box narrative. This file stays a high-level orientation map; `paper/main.tex` is where the actual science accumulates.

## Current studies

### 1. Aspirin ablation (`src/run_ablation_study.py`)

Compares loss/architecture conditions on MD17 aspirin (and, planned but not yet run, benzene/ethanol): `absolute` (plain supervised) vs `absolute+momentum` (adds a momentum-conservation soft loss). `delta`/`delta+momentum` (residual learning against an analytic CHARMM36 baseline, `src/baseline_potential.py`) are commented out of scope - see "Known dead ends" below.

Run: `python src/run_ablation_study.py --smoke-test` first, then `python src/run_ablation_study.py` for the real matrix. Resumable (skips cells whose checkpoint already exists; `--force-retrain` to override). Results land in `results/ablation/summary_table.md`.

**Status:** first 3-seed run (absolute, absolute+momentum) complete on aspirin - confirmed whole-molecule momentum conservation is architecturally redundant (equivariance already guarantees it), which is what motivated moving to the water-box study below. Scope has since been extended to 8 seeds on aspirin + 3 seeds each on benzene/ethanol, not yet run.

### 2. Water-box momentum study (`src/run_waterbox_study.py`)

Tests whether momentum conservation checked *per individual water molecule* in a periodic multi-molecule box is a non-redundant physical constraint - unlike the aspirin case, where TensorNet's equivariance already guarantees whole-molecule momentum conservation for free. Uses `torchmdnet.datasets.WaterBox` (Cheng et al. 2019, PNAS, revPBE0-D3 DFT data, 1593 configs of 64 water molecules each - the same dataset MACE benchmarks against).

Run: `python src/run_waterbox_study.py --smoke-test` first, then `python src/run_waterbox_study.py --force-retrain` for a fresh full run (resumable by default via existing checkpoints, same as the aspirin runner).

**Status: full 6-cell matrix has run to completion, then extended to n=6 seeds, and results exist in `results/waterbox_study/`.** The premise is confirmed: per-molecule momentum violation is many orders of magnitude above the aspirin single-molecule floor (~1e-9), so this is a genuine, architecturally-unenforced constraint here. **Four real bugs were found and fixed getting this pipeline to run at all** (dead download URL, wrong atomic units, non-periodic bond inference, undersized batch/memory - see Lessons below), plus **two checkpoint-selection/monitoring bugs** found after that (Lightning's `save_last` semantics, and a weight-annealing-induced bias in what `ModelCheckpoint`/`EarlyStopping` monitored) - both now fixed in code, see Lessons below. TensorNet's own periodic neighbor search (as opposed to the separate bond-inference/molecule-grouping step) has since been directly verified periodicity-aware, with a precision false-alarm along the way resolved as ordinary float32 behavior, not a bug - see Lessons below and `paper/main.tex` Section~3.4.

**The n=3 "momentum wins on all four metrics" result did NOT survive to n=6** (`paper/main.tex` Section~4.4, `sec:n6-update`) - it turned out to depend heavily on one noisy `water_absolute` seed and on which evaluation lens (raw best-checkpoint, outlier-excluded, windowed-validation) was used. Only a modest force-quality improvement for the momentum condition holds up under every lens tried; max per-molecule violation now favors `water_absolute`, reversed from the original table.

**A first real-dynamics evaluation (NVE rollouts via ASE, `paper/main.tex` Section~4.5, `sec:rollout-results`) found something the static metrics above completely missed**: both conditions produce unstable NVE dynamics from a realistic starting configuration (heating a real ~300K snapshot to somewhere in 1000-2600K within under 1ps, then plateauing) - and the momentum condition consistently runs *hotter*, not more stable, across 10/10 replicate trials on two independent axes (velocity draw, starting configuration). This is now the most pressing open question - see Q3 below.

**Q3 resolved for seed 0, then checked against a second seed** (`paper/main.tex` Section~4.6-4.7, `sec:q3-progress`/`sec:q3-seed5`; Section~5.3, `sec:q3`): the two models' predicted forces agree closely point-wise, at equilibrium AND on real hot rollout frames - two of the three original candidate mechanisms (a force-accuracy tradeoff that only matters off-distribution; momentum "satisfied" by redistributing force within a molecule) don't hold up. A rigorous paired test across 100 held-out configs (not eyeballed means) found the real systematic bias: momentum's net per-molecule force is 0.073 eV/A higher on average (p≈4e-125, 6587 molecule-pairs) - not a general "bigger forces" effect (raw/internal force show the opposite, tiny sign) and not compensated by torque (no significant mean shift there). This isn't decoupled from the static evaluation either: seed 0's own static per-fragment momentum violation was *already* higher for momentum (45.16 vs 41.93) before any rollout was run - the n=6 aggregate favoring momentum is dominated by `water_absolute` seed 2's outlier, and the six seeds individually split ~3-and-3. Seed 0 (used for every rollout up to this point) is one of the three where momentum is worse. **Generalization check (done):** reran both replicate batches on seed 5 (where the static metric favors momentum, 36.28 vs 41.30) via `run_rollout_study.py --train-seed 5` - the rollout-stability gap shrank substantially (plateau-temperature separation went from clean/non-overlapping at seed 0 to mostly-overlapping at seed 5) and the drift comparison stopped being directionally consistent between seed 5's own two replicate axes (unlike seed 0's unanimous 10/10). Verdict at the time: seed-to-seed variation in whether the momentum loss achieves its intended effect, not a fixed property of the method, was the best-supported explanation - though a weak temperature-side lean toward momentum persisted even at seed 5. **That verdict was reached entirely on checkpoints later found to carry two independent confounds (stock ZBL's bonded-pair double-counting; unfair pre-anneal checkpoint selection) - see the Q1-revisited update below, which reverses rather than merely qualifies it.**

**Q4 (new, now top priority): BOTH conditions are dynamically unstable, independent of momentum vs. absolute** - every rollout tried (either condition, any seed, any config) heats a real ~300K snapshot to ~1000-2600K within under 1ps. Literature-supported hypothesis, not yet tested: missing short-range repulsion. Fu et al. 2022 ("Forces are not Enough," arXiv:2210.07237) is the paper predicting exactly this static-accuracy-vs-stability gap; the standard fix in the literature is an explicit ZBL (Ziegler-Biersack-Littmark) repulsive prior, already used by default in both NequIP and MACE (both already cited in this project) specifically to prevent this failure mode, and a recent paper (Yan, Fan & Zhu 2025, arXiv:2504.15925) reports the same robustness benefit directly. **`torchmdnet` (this project's own framework) already ships a ready-to-use `ZBL` prior** (`torchmdnet/priors/zbl.py`), selectable via `prior_model` (currently `None` in `train_waterbox.py`) - needs `cutoff_distance`/`max_num_neighbors`/unit-conversion factors (`distance_scale`/`energy_scale`) to bridge ZBL's native units to this dataset's Å/eV convention, which needs the same empirical verification as the Bohr/Hartree mixup did (don't trust defaults blindly). See `paper/main.tex` Section~5.4 (`sec:q4`).

**Leading hypothesis (literature-grounded, not yet tested further): the chosen cutoff overlaps the O-H covalent bond length, injecting a continuous spurious force onto every bond rather than only correcting rare close approaches.** `verify_zbl_units.py` already showed cutoff_distance=2.0A injects ~2.6 eV onto every O-H bond, always. Checked NequIP's own ZBL implementation (github.com/mir-group/nequip, `nequip/nn/pair_potential.py`) for contrast: it exposes no independently-tunable cutoff at all - it reuses the main model's own graph edges and relies purely on ZBL's own exponential screening decay to vanish before reaching equilibrium distances. That decay length (a = 0.8854*a0/(Z1^0.23+Z2^0.23)) works out to 0.18A (O-H), 0.15A (O-O), 0.23A (H-H) here - an order of magnitude tighter than the 2.0A cutoff used. The common "cutoff = sum of covalent radii" convention gives 0.97/1.32/0.62A for O-H/O-O/H-H - but every one of those sits *below* this project's own empirically-established anomaly floors (0.79-1.8A, see the short-range diagnostic above), meaning that convention would have been too conservative to ever reach the real collapse zone in this system. This looks like a genuine tension specific to a hydrogen-bonded system: the anomalous non-bonded distance and the covalent bond length sit closer together here than in the systems ZBL is normally deployed for (e.g. Yan/Fan/Zhu 2025's positive result used LLZO, a solid electrolyte with no hydrogen-bond network - plausibly why they didn't hit this). Classical force fields (and this project's own `baseline_potential.py`) handle exactly this with explicit bonded-pair exclusion lists; torchmd-net's stock `ZBL` prior has none.

**Bonded-exclusion ZBL variant now implemented, not yet trained/tested.** Literature review (`paper/literature_review_candidates.md` section 0) checked NequIP's and MACE's actual ZBL source directly: neither implements bonded-pair exclusion (their "covalent-radii-normalized cutoff" is a per-pair adaptive cutoff, not a topological exclusion - would not have fixed our overlap problem either); MACE-OFF (MACE's own flagship for covalent organic chemistry) simply doesn't enable ZBL at all; the only real precedent is classical MD (LAMMPS/CHARMM/AMBER zero out 1-2 and 1-3 nonbonded pairs via a topology-derived exclusion list). `src/molecular_zbl.py`'s `MolecularZBL` (subclasses `torchmdnet.priors.zbl.ZBL`) implements exactly this, reusing molecule-membership as the exclusion criterion rather than literal bond type - correct and sufficient for this system specifically, since a water molecule has only 3 atoms (O,H,H), so "same molecule" and "1-2-or-1-3 bonded" are exactly the same set of pairs. Reuses the SAME `local_molecule_ids` tensor already trusted for the per-fragment momentum loss (no second, separately-computed grouping). Registration into `torchmdnet.priors`'s namespace (`register_molecular_zbl_prior()`, monkey-patch, same pattern as `WaterBox.url`/`torch.load` overrides elsewhere in this project) happens both at training-time construction (`train_waterbox.py`) and at every checkpoint-reload call site (`evaluate_waterbox.py`'s `load_waterbox_checkpoint`, shared by `waterbox_ase.py`'s rollout calculator and `analyze_force_decomposition.py`) - a checkpoint saved with this prior needs the name resolvable at reload time too, not just at construction time. Wired through `train_waterbox.py --use-zbl-prior --zbl-bonded-exclusion`, `run_waterbox_study.py --use-zbl-prior --zbl-bonded-exclusion` (writes to a further-separate `checkpoints/waterbox_study_zbl_bonded/` root, never touching the stock-ZBL negative-result checkpoints), and `run_rollout_study.py --use-zbl-prior --zbl-bonded-exclusion`. The masking math (local-index modulo trick + same-molecule check) was synthetically unit-tested locally; the class itself subclasses torchmdnet's `ZBL` directly so it can't even be imported on this Windows checkout - smoke-test on the training box before trusting anything else.

**Second, independent confound found and fixed: checkpoint selection.** Across all 12 `waterbox_study_zbl_bonded` cells, the epoch `val_checkpoint_score` actually selected ranges 17-47 of a 50-epoch budget, essentially by which post-anneal epoch's noisy score happened to dip lowest. The seed-1 pair used above is a clean example: `water_absolute` selected epoch 46 (16 epochs of post-anneal fine-tuning) vs. `water_absolute+momentum` epoch 29 - ONE epoch before `anneal_epoch=30` fires, i.e. zero post-anneal fine-tuning. Not a fair comparison. **Fixed** via `eligible_epoch_start` (`train_waterbox.py`'s `WaterLNNP`): epochs before it are logged as `val_checkpoint_score`=+inf so `ModelCheckpoint` can never select them; `EarlyStopping` now watches the separately-logged unmasked `val_checkpoint_score_raw` instead, so it isn't fooled by the +inf floor into stopping before the eligible window opens. `run_waterbox_study.py --extended-anneal` pairs this with `EXTENDED_NUM_EPOCHS=70`/`EXTENDED_ELIGIBLE_EPOCH_START=50` (unchanged `anneal_epoch=30`, mandatory 20-epoch post-anneal burn-in, real 20-epoch eligible window 50-69), writing to `checkpoints/waterbox_study_..._ext70/`. **Verified working on all 4 retrained cells** (seeds 0/1 x both conditions): every selected epoch (68, 64, 68, 66) falls inside 50-69, and every cell's `post_test.test_y_l1_loss` matches its own `evaluate_waterbox_checkpoint` number closely - no repeat of the seed-0 batch-of-1 anomaly at any of these epochs (suggesting that fragility tracks specific epoch weights, not a fixed property of seed 0 + `water_absolute`).

**The remaining gap has a specific, measured mechanism: a static per-configuration potential-energy offset that NVE converts into heat.** `etot_ev` is essentially perfectly conserved every rollout (drift ~0.001-0.02 eV out of ~30,000 eV) - not an integrator bug. What happens: `epot_ev` drops sharply in the first ~100fs while `ekin_ev` rises by the same amount - the model assigns the real DFT starting config more potential energy than its own nearby learned minimum, and energy-conserving dynamics converts that one-time gap into heat. Confirmed static (not dynamical noise): 5 velocity replicates sharing one geometry give nearly-identical gaps (seed-1 ext70 velocity axis: 11.6±0.37 eV absolute, 9.96±0.24 eV momentum). Confirmed to predict outcome across geometries too: seed-1 ext70 config axis shows a clean monotonic relationship between per-geometry gap and final temperature, independently for both conditions (cfg2: ~2.8 eV gap -> ~430K; cfg4: ~12.6 eV gap -> ~800K; cfg1/3/5 fall in between in the same order).

This is a known, characterized MLIP failure mode, not unique to this pipeline. Literature (verified via primary sources, not just abstracts): Fu et al. 2022 (already cited) established that static test-set accuracy is an average and can't predict single-rollout stability. **Stocker et al. 2022** (*Mach. Learn.: Sci. Technol.* 3, 045010) directly quantify the same disconnect - a model with 0.035 eV/A test force MAE still accumulated >10 eV absolute-energy error during a 300K rollout, describing this as the PES having "holes" invisible to static evaluation. **Raja et al. 2025** (TMLR, arXiv:2402.13984, "StABlE training") studied almost exactly this project's system (64-water-molecule box, same Fu et al. 2022 benchmark) and hit the identical disconnect; their fix isn't more static data but differentiable fine-tuning directly against the model's own simulated trajectories (supervised by an observable like O-H bond length), taking their baseline from 312ps to 1ns stable. The standard alternative in the field is DP-GEN-style active learning (Zhang et al. 2020) - retrain with configs sampled from the model's own rollouts, since a model trained only on pre-existing AIMD snapshots never sees what its own dynamics will explore.

**Decisive check has run - static ENERGY error does not predict rollout heating, but static FORCE error does.** Ran `evaluate_waterbox.py --per-sample` on both ext70 seed-1 checkpoints and pulled the per-sample rows for the 6 configs actually used in the rollouts (`test_config_index` 0-5). Spearman correlation between each config's static per-sample error and its rollout-derived epot gap: `energy_error` gives rho=0.20 (absolute) / rho=-0.14 (momentum) - essentially no relationship, slightly negative for momentum. `force_error` gives rho=0.83 (absolute) / rho=0.71 (momentum) - a real relationship, and the two extremes match exactly and independently in both conditions: config index 2 has the lowest force_error of all 6 (0.389/0.360 eV/A) and the coldest rollout in both (439K/425K, smallest ~2.7-2.9 eV gap); config index 4 has the highest force_error (0.728/0.551 eV/A) and the hottest rollout in both (842K/763K, largest ~12-13 eV gap). Config 4 is actually near-BEST on static energy accuracy (0.73/0.21 eV, among the lowest of the 6) despite being the worst on rollout stability - ruling out "the model gets the energy VALUE wrong at this config" as the mechanism.

**Refined mechanism:** NVE dynamics is driven by forces (the gradient), not energy values - a model can predict the right total energy at a configuration while still having the wrong gradient there, which is exactly what would slide the system toward the model's own nearby basin and convert that force mismatch into heat, independent of whether the energy value happened to be accurate. This sharpens (doesn't overturn) the literature framing above: Fu et al. 2022's own title ("Forces are not Enough") is specifically about force accuracy being the thing static benchmarks under-test relative to what stability needs - this project's own data now directly confirms force error, not energy error, is the relevant static proxy here.

**Next step (not yet run):** given this is now confirmed as ordinary per-configuration force error (not a static-metric-invisible dynamical artifact), the real fix is DP-GEN-style active learning on the model's own rollout trajectories (retrain including configs sampled from currently-overheating rollouts, prioritizing the force loss there) or StABlE-style stability-aware fine-tuning (differentiable fine-tuning against the model's own simulated trajectories). Neither ZBL nor the anneal fix was ever expected to close this gap - both correctly fixed separate, real bugs instead. n=6 configs is small; worth checking this correlation holds at a larger sample (e.g. run the per-sample force_error against a much larger set of rollout starting configs, or at minimum via the already-available momentum/absolute-seed-0/other-seed checkpoints) before treating it as fully established.

2. Q1, downgraded: whether the momentum loss's static-metric improvement is real at all - see the n=6 update above. Not fully closed out (energy conclusion is methodology-dependent), but no longer the main thread.

**Resolved:** TensorNet's own periodic neighbor search (previously never directly verified, only the separate bond-inference/molecule-grouping step had been) is now confirmed periodicity-aware - `src/verify_periodicity.py`, `paper/main.tex` Section~3.4 (`sec:periodicity`). Method: translate a single molecule by one full lattice vector, unwrapped, and check energy/force predictions are unchanged (they were, to ≤0.006 eV / ≤9e-5 eV/Å - float32 noise) versus a half-lattice-vector negative control (2.9-5.25 eV / up to 11.7 eV/Å, ~500-1500x larger, confirming the test is sensitive). ## Lessons learned the hard way (don't repeat these)

- **Always call `super()`** when overriding `on_validation_epoch_end`/`on_train_epoch_end`/`on_train_epoch_start` on an `LNNP` subclass - skipping it silently drops base-class metric logging, which surfaces later as a confusing "metric not available" crash somewhere unrelated. Caught this exact mistake mid-edit once already this project (`train_waterbox.py`'s `on_train_epoch_end`) - re-check every new hook override.
- **`val_total_mse_loss` is not comparable across conditions whose loss composition differs** - true both for delta-learning vs. absolute-mode (delta residualizes the targets) and, newly discovered, for **any run using energy/force loss-weight annealing**: the metric is `w_E * val_y_mse + w_F * val_neg_dy_mse` using *whatever weights are currently active*, so its meaning shifts at the exact epoch an anneal schedule changes those weights - structurally biasing "best checkpoint" selection toward whichever phase has the smaller/calmer weighted sum, independent of actual model quality. Fixed in `train_waterbox.py` via `val_checkpoint_score`, a version that always uses the run's *original* (pre-anneal) weights, so "best" means the same thing on every epoch. `ModelCheckpoint`/`EarlyStopping` now monitor that instead. For non-annealed runs this is a no-op (identical to `val_total_mse_loss`).
- **Lightning's `ModelCheckpoint(save_last=True)` does not mean "always save the current epoch."** Per Lightning's own docs, it "saves a last.ckpt copy whenever a checkpoint file gets saved" - under `save_top_k=1`/`mode="min"`, that means `last.ckpt` only updates on genuine improvement, same gating as the "best" checkpoint. If the true best epoch happens early and nothing ever beats it, `last.ckpt` silently freezes at that same early epoch, indistinguishable from "best" - not actually the final epoch. To get a real, unconditional "current epoch, no matter what" checkpoint, use a *second*, separate `ModelCheckpoint(monitor=None, save_top_k=0, save_last=True)` - `monitor=None` combined with any `save_top_k` other than `None`/`-1`/`0` raises `MisconfigurationException`, so `save_top_k=0` specifically is required.
- **`val_total_mse_loss` is not a fair metric across delta-learning vs. absolute-mode conditions** (delta-learning residualizes the target labels). Use `val_force_mae` as the shared checkpoint-selection metric when conditions mix the two; fine when every condition being compared is absolute-only.
- **MD17's native frame spacing is 0.5 fs**, not 0.1 fs - every rollout `dt` default in this repo was fixed from 0.1 to 0.5. If you add a new rollout/eval entrypoint, default its `dt` to 0.5.
- **Any new upstream dataset's file format doesn't guarantee its usual unit convention** - the WaterBox dataset's raw `dataset_1593.xyz` wears a quippy-style extended-xyz header (implies Angstrom/eV by convention) but is actually in raw Bohr/Hartree atomic units, a hand-serialized CP2K dump that was never actually unit-converted. No documentation stated this - it was confirmed empirically against physical priors (box density, O-H bond length, force magnitude order). Check new datasets the same way before trusting them.
- **Any utility written/tested against MD17 should be assumed non-periodic-only until explicitly checked** against periodic data - it won't crash, it'll silently give a wrong answer (bond inference misgrouped molecules straddling a periodic box face, using plain Euclidean distance instead of minimum-image convention) that only a downstream sanity assertion happened to catch.
- **Hyperparameters that scale with per-example graph size (batch size, `max_num_neighbors`) need re-deriving per system, not inherited from a prior study just because the scientific question is the same.** TensorNet's per-edge tensor representation plus a denser/larger system (192-atom periodic water box vs. 21-atom aspirin) blew the aspirin study's `batch_size=32` out to a ~45GB single-pass memory requirement. When diagnosing GPU OOM, prefer directly measuring `torch.cuda.memory_allocated()/memory_reserved()` growth over guessing from the OOM message alone - it's genuinely ambiguous between a leak, a legitimate steady-state need, a worst-case-tail batch, and simply running on the wrong device (`CUDA_VISIBLE_DEVICES` not making it into a particular shell invocation is a real, confirmed failure mode here - check the `LOCAL_RANK: 0 - CUDA_VISIBLE_DEVICES: [...]` line Lightning prints at startup).
- **Fixed, unchanging energy/force loss weighting for an entire run is a known predictor of exactly the kind of energy-calibration instability seen here** (energy oscillating by orders of magnitude epoch to epoch while force stays stable, under a fixed 0.05/0.95 split). Current practice in MACE and NequIP addresses this by *annealing* the weighting (force-dominant early, energy-dominant later) rather than holding it fixed - implemented here, see `paper/main.tex` Section 2.3 for the schedule and citations, and Section 4/5 for whether it worked.
- **When comparing conditions, don't trust a "best checkpoint" mean/std across seeds without first checking whether checkpoint selection is itself noisy.** Confirmed: `val_total_mse_loss`/`val_checkpoint_score` oscillate by 1-3 orders of magnitude epoch to epoch in this pipeline, so "best" can be a lucky noise-dip rather than a converged state. More seeds does not fix this (it just gives a more precise estimate of a still-noisy quantity) - a windowed/median comparison over raw unweighted per-epoch metrics (already logged, zero extra cost) is a better free diagnostic than either trusting the single best-epoch number or running more seeds blindly.
- **Report energy error normalized per-atom or per-molecule, not as a raw system-wide total**, when comparing against literature (e.g. MACE reports meV/H2O) - this project's own raw per-configuration totals aren't directly comparable to published numbers without that conversion.
- **New ablation/study runners should, from the start:** persist results incrementally (not once at the very end), skip already-completed cells by default (resumable), and wrap each cell in try/except with a full traceback on failure.
- **Vectorize anything called once per training batch.** Python loops over individual bonds/atoms/molecules inside the hot training loop are the direct cause of this project's worst compute blowups.
- **Before treating a suspiciously "quantized-looking" numerical result as a precision bug (TF32/fp16/reduced-precision computation), check the absolute magnitude of the number involved and compute the expected plain-float32 rounding floor (`|value| * 2**-23`) at that magnitude.** A diff pattern that lands on a clean grid doesn't require reduced precision anywhere - it can just be float32's fixed absolute step size showing up near a large fixed magnitude. Caught here: `verify_periodicity.py`'s residual energy diffs looked quantized to exact multiples of 2^-9 eV; turned out to be exactly what plain float32 predicts for this model's ~-30,000 eV absolute energy scale (`remove_ref_energy=False` means the model predicts raw total energy, not a small residual near the eV-scale MAE numbers reported elsewhere) - not a bug.
- **When a study script's "run N replicates" loop needs multiple independent sources of randomness (which starting config, what initial velocities), give each its own explicit seed parameter - don't reuse one `seed` for both.** Conflating them in `rollout_waterbox_ase.py`'s first version meant varying `seed` to get different velocity draws silently varied the starting geometry too, since the same seed also drove the train/val/test split. Caught via a 335K vs. 292K starting-temperature mismatch between two runs that were supposed to be identical. Now `seed` (data split) and `velocity_seed` (Maxwell-Boltzmann draw) are separate parameters.
- **ASE's `MaxwellBoltzmannDistribution` draws from whatever state numpy's global RNG happens to be in unless you pass `rng=np.random.RandomState(seed)` explicitly** - it does not default to anything tied to your own seed. Without it, two "identical" rollouts silently start from different velocities, confounding any cross-checkpoint comparison.
- **ASE's `dyn.run()`/`irun()` already calls every attached observer once at `nsteps==0` before the first integration step** ("for historical reasons", per its own source comment) - an additional manual pre-call before `dyn.run()` produces an exact-duplicate step-0 row/frame, not a defensive safety net.
- **`ase.geometry.rdf.get_rdf` accepting a list of `Atoms` to average over is a >=3.28.0 feature; older installs don't reject a list with a clean `TypeError` - they accept it and fail deeper inside with `AttributeError` (`'list' object has no attribute 'cell'`).** Catch both, not just `TypeError`, when writing a version-tolerant fallback.
- **`get_rdf`'s minimum-image convention requires `rmax < (box edge)/2`, and box size varies configuration-to-configuration in the WaterBox dataset (observed ~9-14 A, not a single fixed value)** - compute the safe limit from whichever frames are actually being used, not a fixed constant tuned against a handful of samples. A fixed 6.0 A default hit `CellTooSmall` on the training box on the very first real batch run.
- **A "shift every atom by a lattice vector and wrap the whole system back into the cell" test of periodicity is a no-op**, not a real invariance check - it reproduces the exact same absolute coordinates you started with. The real test: move a *single* molecule by an unwrapped lattice vector and leave everything else untouched (see `verify_periodicity.py`).
- **Running more seeds/replicates doesn't just narrow error bars - it can overturn the conclusion entirely, and has, twice, in this project.** The water-box static-metric "momentum wins on all 4 metrics" result (n=3) turned out to be substantially driven by one noisy seed once n=6 was available; a single-trial NVE rollout comparison flipped which condition showed less energy drift once a velocity-draw confound was fixed. Treat any n=1-3 comparison in this codebase as provisional until replicated.
- **When comparing two models' behavior on data one of them generated (e.g. a rollout trajectory), cross-evaluate both models on both datasets, not just each model on its own output.** A same-model-on-own-trajectory comparison conflates two different questions - "does this model's force response change on this kind of geometry" vs. "are the geometries this model's own dynamics reaches different from the other's" - either one alone can produce a misleading correlation. `analyze_force_decomposition.py --mode trajectory` does this by running both checkpoints on frames from both conditions' saved rollouts.
- **A pattern that's consistent in direction across many independent replicates (10/10, not just a large mean) is evidence of a systematic effect, not undirected chaos/noise - the two are distinguishable and matter for where to look next.** If two nearly-identical models differed only by noise with no consistent bias, sensitive dependence in the nonlinear MD dynamics would amplify that noise in whatever direction it happened to point, so the *sign* of any resulting divergence should vary randomly across independent replicates (different starting configs/velocity draws). Getting the same sign in all 10 replicates (`run_force_decomposition_study.py`'s frame-180 result) rules out pure chaos and implies a small, repeatable, currently-unidentified bias between the two models' forces - worth stating explicitly since "these are chaotic dynamics, differences are expected" would have been a plausible-sounding but wrong way to wave this finding away.
- **When a single-seed result looks like it contradicts a multi-seed aggregate, check that seed's own individual number before assuming there's a real contradiction to explain.** The Q3 force-decomposition work (seed 0 only) found momentum with *higher* net force than absolute - looking like a reversal of the n=6 study's aggregate "momentum has lower mean_per_molecule_momentum_violation." There was no contradiction: seed 0's own static evaluation had *already* shown momentum higher (45.16 vs 41.93) before any of this rollout work started; the aggregate favoring momentum was dominated by an unrelated seed's outlier, and the six seeds individually split ~3-and-3. Spent effort looking for a compensating mechanism (checked net torque) before checking the one piece of already-available data that dissolved the puzzle immediately - check the cheap thing first.
- **A diagnostic that reports the same "first violation" at t=0 for every single trajectory, across multiple independent starting configurations, is telling you about the diagnostic's calibration, not about the trajectories.** `diagnose_short_range_collapse.py`'s first real run (42/42 trajectories) reported this, which sounded like a clean confirmation until checked directly - t=0 is the real, unheated DFT starting snapshot itself, before any model dynamics happen, so a "model-caused collapse" literally cannot be detected there. Two independent calibration bugs were responsible: (1) excluding only literal covalent bonds isn't enough when checking a same-element pair like H-H - a water molecule's own two hydrogens sit ~1.5 A apart purely from the H-O-H bond angle, with no bond between them, so every molecule's own H...H polluted the statistic from frame 0 onward; the fix is excluding by molecule membership (`infer_molecule_groups`), not just by literal bonds. (2) a threshold built from a percentile over every individual pairwise distance pooled across many reference configs, then checked against each frame's own *minimum* distance, mixes a population percentile with an order statistic - the minimum of a few thousand pairs will sit below a threshold that only excludes 0.1% of a much larger pool almost regardless of whether anything is actually anomalous. The fix: compute each reference config's own minimum first, then take a percentile over that much smaller pool of per-config minima - the same statistic on both sides of the comparison. General lesson: when a per-frame/per-sample "anomaly" check reports the anomaly present at frame 0 (before anything could have happened) or uniformly across every sample regardless of condition, that is itself informative - check the calibration before trusting the substantive result.
- **`paper/main.tex` used `\citet`/`\citep` (natbib commands) in several places without `\usepackage{natbib}` in the preamble** - would have failed to compile the first time anyone actually ran `pdflatex` on it, undetected until now because no LaTeX compiler exists in this checkout. Added the missing `\usepackage{natbib}` (required anyway by `\bibliographystyle{plainnat}`, itself a natbib-specific style). A structural-integrity script (balanced `\begin`/`\end`, no dangling `\ref`/`\cite` targets - see the workflow used throughout this session) doesn't catch missing-package bugs like this one; worth a mental double-check of "does every command used actually have its package loaded" when editing the preamble or adding new citation commands, since nothing here will complain until an actual LaTeX compiler is available.

- **A huge (thousands-to-tens-of-thousands of eV) energy MAE from a 1-2 epoch smoke test is expected, not a bug, for this model.** `remove_ref_energy=False` means the model predicts raw total energy on a ~-30,000 eV absolute scale, not a small residual - a barely-trained checkpoint hasn't learned that scale yet. Confirmed by comparing the bonded-exclusion-ZBL smoke test's `energy_mae=16060 eV` against the (separately, previously investigated) stock-ZBL seed-0 checkpoint's own epoch-0 `val_y_l1_loss=25732 eV`, before that checkpoint's real anomaly ever showed up (which only appeared after full 48-epoch training) - same order of magnitude, confirming this is just what an undertrained checkpoint looks like, independent of ZBL/bonded-exclusion. A smoke test's only real job is confirming the pipeline runs without an exception; don't read its accuracy numbers as a signal either way.

## Known dead ends (don't re-attempt without a reason)

- **Delta-learning on aspirin**: correct in principle, computationally intractable in this implementation (~50h/epoch, vs ~45-70min/epoch for absolute mode) due to `baseline_potential.py`'s unvectorized baseline calculation. Would need that file vectorized first.
- **Momentum-conservation loss on a single isolated molecule**: architecturally redundant with TensorNet's equivariance (confirmed empirically). Testing a different single isolated molecule (any MD17 molecule) would not change this - the water-box study exists specifically to test a setting where it *isn't* redundant.
